How it works

Chats

  1. The desktop view lists shared chats first, then local projects and chats. It detects installed Codex and Hermes adapters. A new chat can use a selected project or the home folder. No harness setup form or working folder setting is required.
  2. The room directory records each chat's creator. The People list marks that person as owner for that chat. Only that owner can rename it. A rename emits a room event so connected members see the new title.
  3. A person writes through the :o composer. The room bridge sends shared messages to the service, which orders them and delivers them to authorized members. The local SQLite cache applies each event in order.
  4. In a one-person chat, the selected harness can answer an ordinary message. In a group chat, a person mentions a harness. Mention matching follows the cursor, including an @ before existing text or an @ followed by a space. The room queues one harness turn at a time.
  5. Invite friend shares a native Codex or Hermes chat by importing its readable history into a room. An invite grants access to that chat. The room service still calls harness participants agents in its internal protocol.

Harness turns

  • Harness registration creates stable internal participant IDs for installed Codex and Hermes adapters. Saved IDs remain claimable for older shared chats. The interface names each harness with its owner, such as Aman's Codex, in replies, mention suggestions, and the harness list, and marks it idle, queued, or working.
  • When a queued turn starts, the runner sends the unseen completed shared messages to the native adapter. A single new message goes through as written. Multiple messages keep their source participant labels. The runner adds no generated identity or shared-chat instruction preamble.
  • Codex app-server and Hermes ACP emit reply text as it arrives. The runner batches small deltas for 80 milliseconds before appending ordered chunks to the room. The chat displays these chunks inside one reserved reply.
  • For a Codex session already owned by Codex Desktop, the desktop link submits the turn to that owner and copies saved assistant text into the room as the session file grows. This path can only display text after Desktop has saved it. :o does not write the native session file.
  • New local chats use native chat control. The selected adapter owns its session. Permission requests are handled by the owner computer.

Chat copies

  • Every committed room message and reply update refreshes an app-owned JSON context copy for Codex and Hermes under the :o profile. Each copy contains ordered text, source participant IDs and names, state, and the applied event sequence.
  • The native Codex and Hermes session journals remain owned by those tools. Shared messages that arrived while a harness was idle are included on its next requested turn through the adapter.
  • Sheep reads local projects, chats, and selected native history. The catalog shows its saved copy first and refreshes discovery in the background.

Hordes

  1. The top-bar Hordes tab opens a project offering. Project cards link to goals, GitHub repositories, collaborators, skills, orchestration and budget commitments. Project ideas are labeled proposals and can prefill a new project.
  2. The local bridge calls the authenticated Hordes service. Its SQLite tables store project definitions, member roles, independent budget units and discussion messages. Source code stays in Git and local working copies.
  3. The creator is Horde Warchief. Warlords can edit, Warriors can contribute and discuss, and Scouts can read. The service checks permissions. Edits use revisions; messages deduplicate retries; deletion is recoverable from Trash.
  4. Budgets are commitments, not payments or metered spending. Five predefined strategies describe work; automatic execution and a custom strategy editor remain future work. Project skills store instructions and tool names without granting tool access.
