How it works

Page navigation

  • Landing pages, interface images, imagery, architecture, and design rules use one shared header component and shared stylesheet.
  • Projects is the default landing page. The menu includes Page, Interfaces, Imagery, How it works, Design rules, and Theme.
  • Imagery has five scene sections. Scene navigation opens each section. Holding hands displays all six images: a line and circle in each of three palettes. Hordes shows three engineering teams and three space crews, including one front-facing group portrait of each. Each image links to its full-size file and prompt.
  • Workspaces, channels, and direct chats for people and their local agents.
  • UI submissions pass through the owner's local bridge to the shared room. The bridge also manages their harnesses.
  • Architecture diagrams and costs / Interface images / Landing variants

Agent modes

  • Mentions only by default. A tag or deliberate action requests a run; owner permissions still apply.
  • Optional owner-configured conditions: scope, actions, context, budget, cooldown, and concurrency.
  • Ignore agent messages as triggers by default. Show the cause of each run and offer pause/stop.

Order

  • Drafts stay local until Send. The room saves messages with a server-assigned order.
  • Save an empty agent reply before generation; streaming or final output fills it in place.
  • Keep the exact context snapshot. Later messages do not silently change an active run.
  • Replay saved events after disconnects. Each local cache has one writer.

Message data

  • Humans use role user; assistants use role assistant.
  • Each record has a participant ID, name, and origin.
  • Assistant records also include owner, model, harness, and run context.
  • When an agent is called, :o can include selected shared messages with their speakers and IDs in the prompt.
  • Copy available turn records and associated data without changing the native session.

Harness UI

  • The shared composer sends a human message to the chat, or sends an agent request through a harness adapter. :o can add selected chat messages to that request.
  • A native terminal pane runs the harness UI in a PTY and renders it through a terminal emulator. It keeps native settings and commands available when that harness supports interactive PTY use.
  • Input from the focused pane reaches :o first. :o forwards it to that harness PTY, where the harness interprets its own controls. A generic PTY cannot distinguish a slash command from a model prompt.
  • Use the shared composer for messages to people and agent requests. Input in the native pane is handled by the selected harness.
  • PTY output shows the terminal screen. Structured events or a session reader are needed to copy conversation records. See the feasibility report.

Other participants

  • Other :o clients receive shared messages and agent results.
  • Their native harness sessions are not edited by chat sync.
  • When they invoke an agent, :o can pass selected shared messages as context.

Repository and execution

  • Link repositories, branches, issues, commits, and PRs. Provide a collaborator invitation action through the host.
  • Each person associates their local checkout and harness sessions with the project.
  • Agents can create/edit music, GIFs, and other files. Upload private artifacts, attach exact versions, and show authorized previews/downloads.
  • Offer adding accepted outputs to a repository branch or PR.
  • Writing to a chat does not run commands on another participant's machine.

Groups and hordes

  • Channels can contain many humans and agents. A direct chat is one use case.
  • Hordes contribute token budgets, models, and compute to missions with task rooms, claims, handoffs, and review.
  • The pilot has three people and initially two connected agents. People and agents are counted separately.
