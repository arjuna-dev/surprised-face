How it works

Desktop app

  • The chat view keeps the green logo visible, lists recent projects with their chats nested under the selected project, and opens Projects by default. Chats with invited people appear under Chats.
  • Selecting a project opens a ready composer with project and agent selectors. New chat clears the draft; the plus icon on a project opens a draft in that project. The first message creates a native Codex or Hermes session through native chat control, then sends through that adapter. The local catalog preserves the new chat across restarts.
  • Click Settings again or use Back to chat to leave Settings. Harness sign-in, including Codex sign-in, is in Settings. The local catalog refreshes at startup and once per minute.
  • The composer stays at the bottom and People and agents is collapsible. Existing native chats resume their session and stream answers through the adapter. Sheep reads saved history internally; raw source records and injected project setup instructions are not shown in the chat.
  • Project listing hides stale and internal folders and sorts by recent chat activity. Each chat belongs to its most specific tracked project. Chats with no matching project appear under Other local chats.
  • Appearance offers Mint + charcoal by default, Cobalt + red, and Classic. The packaged app includes its local reader executable.

Chat invites

  • The Invite friend icon generates a one-use code for the current chat, copies it to the clipboard, and briefly shows Invite code copied. There is no persistent code panel. The code expires after seven days. The recipient joins only that chat and can read its existing history.
  • Inviting from a native Codex or Hermes conversation imports its readable transcript and links the existing native session to the chat's agent. The app creates a chat account automatically when needed; users do not configure Cloudflare.
  • Join a chat opens a form for the invite code and, on a new profile, the person's name. Joining opens that chat directly. The membership and invite routes check membership before messages, events, WebSocket connections, and agent mentions.
  • A one-person chat calls its sole owner agent automatically. After another person joins, agents run on explicit mentions. The owner must enable remote agent requests on their computer.
  • The local bridge queues human messages during disconnections. Delivery acknowledgement refreshes the chat and removes its pending copy without waiting for another message.

Page navigation

  • Landing pages, interface images, imagery, architecture, and design rules use one shared header component and shared stylesheet.
  • Projects is the default landing page. The Page menu also includes Friends, Hordes, and Orchestra for local multi-harness collaboration. The review-page Theme control switches Blue/red or Green.
  • Imagery has five scene sections. Scene navigation opens each section. Holding hands displays all six images: a line and circle in each of three palettes. Hordes shows three engineering teams and three space crews, including one front-facing group portrait of each. Each image links to its full-size file and prompt.
  • Chat membership controls access to each shared conversation. The directory stores identities and agent metadata.
  • UI submissions pass through the owner's local bridge to the shared room. The bridge also manages their harnesses.
  • Architecture diagrams and costs / Interface images / Landing variants

MVP base

  • Three people, one named agent per person, initially using Codex or Hermes.
  • The copied Electron/Vue app contains the shared chat, settings, and native adapters.
  • :o starts bundled Sheep with sheep bridge --stdio and exchanges JSON over stdin/stdout. This uses Sheep as a background process; its interactive terminal UI is not embedded in :o.
  • Sheep lists projects/chats and returns portable transcripts. It reads selected native session records in pages. Original harness files remain read-only; the compact transcript and handoff flow are unchanged.
  • Reading a selected session adds local I/O and parsing. Rich records are not loaded for every list item. Performance has not been measured; some paged readers may rescan earlier data.
  • Sheep bridge and reader details / Participant tags and both themes.

Agent modes

  • In a one-person chat, an ordinary message runs the chat's owner agent when one is selected or is the sole available agent. In a group chat, an explicit @agent mention queues a turn.
  • The agent owner can disable requests from other members while continuing to use their own agent. Optional conditions and automatic group participation are planned.

Order

  • Humans can send at any time, including while an agent is streaming.
  • The room saves messages in server order. Solo chat messages can queue the owner agent; group messages require an explicit mention.
  • Only one agent turn runs per chat. Other agents wait until it finishes, fails, or is confirmed stopped.
  • When a turn starts, capture the completed chat context and save its empty reply at the end of the chat. Streaming or final output fills that position.
  • New human messages appear after the active reply and do not change its prompt.
  • Queued turns use the completed conversation available when they start. Reconnects replay saved events.

Message data

  • Humans use role user; assistants use role assistant.
  • Human messages store participant ID and name. Agent replies store agent ID and name, owner, model, and harness.
  • The room stores the ordered shared conversation. The local SQLite copy applies saved events in sequence.
  • When an agent is called, its owner app sends the completed room context through that agent's native harness adapter.
  • Harness files remain harness-owned. Sheep reads selected history without writing to those files.

Harness control

  • Each local agent selects Codex or Hermes, a model, and a working folder in Settings.
  • :o sends agent requests through Codex app-server or Hermes ACP and streams results into the shared chat.
  • The agent owner handles permission requests on their computer. Remote requests run only when that owner enables them.
  • The shared chat does not embed the harness terminal UI, slash commands, or hotkeys. Additional settings and commands need explicit adapter support.
  • See the harness interface notes.

:o can keep one outer layout for chat and routing. Use a versioned adapter manifest for known built-ins and query runtime catalogs where available. Do not scrape the TUI for its menu. More detail and source links are in the feasibility report.

Other participants

  • Other authorized :o clients receive the chat's messages and agent results.
  • Their native harness sessions are not edited by chat sync.
  • When they invoke an agent, :o can pass selected shared messages as context.

Repository and execution

  • Link repositories, branches, issues, commits, and PRs. Provide a collaborator invitation action through the host.
  • Each person associates their local checkout and harness sessions with the project.
  • Agents can create/edit music, GIFs, and other files. Upload private artifacts, attach exact versions, and show authorized previews/downloads.
  • Offer adding accepted outputs to a repository branch or PR.
  • Writing to a chat does not run commands on another participant's machine.

Planned groups and hordes

  • Hordes would contribute token budgets, models, and compute to missions with task rooms, claims, handoffs, and review.
  • The pilot plan has three people and initially two connected agents. People and agents are counted separately.
