# :o Feature Wishlist

Working priorities for workspaces, channels, direct chats, and local agents. The first pilot has three people and at least two connected agents. Community missions coordinate contributed token budgets, models, and compute.

| Priority | Feature | Wishlist outcome | Notes and guardrails |
| --- | --- | --- | --- |
| P0: First proof | :o CLI middleware | Make `:o` the user's entry point for shared chat and multiple local harnesses, with a consistent outer UI. | Every submitted message enters `:o` first. Human messages go to shared chat. Agent requests go through the selected adapter with chosen chat context. |
| P0: First proof | Harness connections and capabilities | Represent each installed or authorized harness runtime separately from its harness type and native sessions. | Record owner, device, model, and capabilities such as PTY display, structured events, prompt submission, settings, command discovery, resume, interruption, and approvals. |
| P0: First proof | Per-harness command and settings adapters | Expose the `:o` commands and settings supported by the selected harness. | Use runtime APIs and catalogs where available, plus a versioned manifest for built-ins that lack discovery. Keep the native PTY pane for controls not yet implemented. |
| P0: First proof | Native harness terminal pane | Keep harness-specific interactive controls available inside the `:o` app. | Render the child PTY with a terminal emulator. `:o` routes pane input to that harness. Use the shared composer for agent requests because a generic PTY cannot distinguish commands from model prompts. |
| P0: First proof | Multi-party :o chat data model | Combine human messages and copied harness records in one shared `:o` conversation. | Add participant ID and name to every record. Preserve available source data and associated tool records. Assistant metadata includes model, harness, owner, and origin. Human-only chat entries originate in `:o`; agent turns come through the selected harness. |
| P0: First proof | Private invitations | Let an owner invite specific people to a workspace, channel, or direct chat and authorize their own harness connections separately. | No public listing by default. Support revoking chat and harness access independently. Chat access does not grant machine execution. |
| P0: First proof | Live shared chat | Let participants follow a shared conversation and send messages from their `:o` clients. | A chat-only message stays in `:o`. A separate action sends a request to a chosen harness. Keep chat access separate from permission to run commands on another person's machine. |
| P0: First proof | History import and consent | Let an owner select native conversation history and associated data to import into a shared chat. | Preview the records and attachments before sharing. Ongoing shared messages are created through `:o`; imported harness history keeps its source attribution. |
| P0: First proof | Basic workspace and channel membership | Invite the three pilot humans to one workspace and private project channel; support direct chats too. | Multiple humans and agents are the general model. Keep room authorization explicit. |
| P0: First proof | Mention-only agents | Agents act only when tagged or deliberately invoked by default. | Check owner permission and spending limits; show owner, context, and reason for starting. |
| P0: First proof | Stable message order and replay | Save empty agent replies before generation and fill them in place; all clients apply the same saved events. | Server sequence, command deduplication, frozen context, chunk order, durable outbox, leases, and reconnect replay. No shared transcript file writes. |
| P0: First proof | Music, GIFs, and file sharing | Create or edit media with an agent and publish it in chat. | Private uploads, authorized previews/downloads, provenance, immutable versions, and links or PRs for canonical project assets. |
| P0: First proof | Human notifications | Unread messages, mentions, and optional local notifications. | Keep human messages visible alongside agent activity; allow channel mute and separate run completion/failure preferences. |
| P1: Collaboration | Configured agent conditions | Owners opt into event rules or meaningful-contribution detection. | Scope by channel and action; detection budget, cooldown, concurrency cap, causal chain limits, pause, and stop. Ignore agent messages by default. |
| P1: Personal use | Cross-device workspace | Let one person find and follow shared chats, repository links, and local sessions on another device. | `:o` clients receive shared messages. Viewing from another device does not itself authorize harness execution. |
| P0: First proof | Repository links and collaborator invitations | Link a chat or mission to a canonical GitHub or similar repository, branch, issue, commit, or pull request. | Expose the host's collaborator invitation flow beside the repository. Code and canonical assets stay there; changes use branches and review. Chat and repository permissions remain explicit. |
| P1: Personal use | LLM project associations | Associate one repository and :o chat with each participant's own harness project or workspace. | A shared chat can connect multiple private workspaces. Instructions, files, and native history are shared only with their owner's consent. |
| P1: Personal use | Assistant participation through a harness | Let a person route a request from `:o` to one of their connected harnesses and see its response in the shared chat. | Include selected shared-chat context when the agent is invoked. Show whose model usage is consumed. Preserve the native record and add participant, model, and harness attribution in `:o`. |
| P1: Personal use | Portable session snapshot or fork | Start a new session in another harness using an approved transcript and context. | Preserve the original session. Do not promise migration of private, harness-specific state. |
| P1: Personal use | Desktop app | Provide a desktop interface to discover local projects and sessions, link them to repositories, review sharing scope, and follow collaboration. | Keep local resource access under the device owner's control. |
| P2: Organizations | Organization workspaces and permissions | Give teams shared projects, member roles, and controls for who can view chats or connect native chat sources. | Keep organization access separate from project, conversation, and execution permissions. |
| P0: First proof | Slack-like collaboration UI | Organize workspaces, project channels, group chats, and direct chats around people and agents. | Human messages are sent through `:o`; selected agent output is attributed to its harness and model. |
| P2: Collaboration | Approval and activity history | Record invitations, access changes, mission requests, approvals, and submitted results. | Require explicit human approval for consequential actions such as running remote commands or merging changes. |
| P3: Community missions | Horde missions and task graph | Break a shared goal into bounded task rooms with dependencies, atomic claims, leases, budgets, and reviewable deliverables. | A horde coordinates contributed agent runs. Link tasks to repository artifacts and keep mission summaries separate from per-run streams. |
| P3: Community missions | Paid model usage and compute contributions | Let contributors bring their own paid inference budget, local models, or suitable compute to a shared mission. | Paid token usage is a recurring cost. Models are broadly available, while harnesses and skills are usually free or low cost. Never pool or expose provider credentials. |
| P3: Community missions | Mission task delegation | Assign bounded tasks to willing contributors who can spend model usage or compute on the mission. | Contributors can self-fund usage or use an explicitly funded project budget, then submit a reviewable artifact. |
| P3: Community missions | Mission work handoffs | Pass task context, progress, and artifacts between contributors and their local harnesses as mission ownership or capacity changes. | Handoffs matter here because they move work to people who can contribute paid model usage or compute toward the shared goal. |
| P3: Community missions | Contribution and validation view | Show task ownership, contributed model or compute capacity, linked branches and pull requests, test results, review status, and mission progress. | Progress should be based on inspectable outputs, not agent claims alone. |
| Explore | Public chat discovery | Let people find public :o chats and mission discussions associated with a repository or topic. | Discovery is for chats and discussions. Repository content stays on GitHub or a similar host, with access governed there. |
