Stack

Workspaces, channels, and direct chats with people and their local agents.

Every participant has an owned local bridge. This diagram shows two; a room can have many. UI traffic goes through its bridge, which also manages that person's harnesses.

Vue

  • No requirement here favors React. Your preference for Vue is sufficient.
  • Vue components fit the shared chat, drawers, streaming messages, and media previews. Vue guide.
  • Use Vite for the app and build. These static proposal pages remain plain HTML. Vue tooling.

Connections and local UI

UI to bridgeCLI/desktop uses local IPC; a local web UI uses a paired loopback endpoint with origin and token checks. A web page cannot launch a harness by itself.
Bridge to cloudOutbound WebSockets over TLS. Authenticate every subscription and command. No inbound port on a contributor's machine.
FallbackHTTP commands + SSE events can use the same ordered protocol.
WebRTCLater voice or live media. Shared chat still needs durable server order and history.

Storage

  • The cloud room log is authoritative for shared chat. Local views apply the same saved events.
  • Each local cache has one writer. Exported JSON is rebuilt from events, not edited concurrently by participants.
  • Harnesses keep their own native sessions. Use adapters for runs and imports; do not inject metadata into native session files.
  • Model keys and tools remain on the owner's machine. Remote requests use explicit permissions.

Message order

One room saves the order. Each participant connects through their own local bridge.

  1. Alex sends a request through bridge A. The room saves the request and an empty agent reply #42 before generation.
  2. Both bridges receive the same saved messages. Bridge A starts the approved harness run using its recorded context.
  3. Jo sends a human message through bridge B. The room saves it as #43, after #42.
  4. Bridge A sends output for #42. The room saves each batch and sends it to both bridges. Each UI fills #42 in place.
  5. If streaming is unavailable, #42 stays empty until the final output arrives. It never moves after #43.

The room assigns order in a short storage transaction, then acknowledges and broadcasts. Use SQLite transactions; never hold one while waiting for a model.

      Three different kinds of order

      FieldPurpose
      event_seqEvery committed event. Reconnect from the last applied event; fill gaps before continuing.
      message_seqOnly message creation. Keeps chat positions stable as streaming events arrive.
      chunk_indexOrder inside one reply. Duplicate or out-of-order chunks cannot overwrite another message.

      Context and concurrent runs

      • Freeze an explicit context snapshot when a run is accepted: exact text, included message revisions, attachment references, and the event frontier.
      • Include completed messages by default. Partial agent output enters another prompt only if deliberately selected and captured as a fixed snapshot.
      • Record the native session ID and turn frontier too. Capture the actual adapter request when execution starts; existing harness history can affect a reply beyond the shared snapshot.
      • A message arriving mid-run appears in the chat but does not silently change the running prompt. A later run can include it.
      • Allow agents on different sessions to work concurrently. Queue runs on the same native session.
      • Typing is a local draft. Presence and typing indicators are ephemeral, not committed messages.
      • Separate messages need ordering and deduplication. CRDTs become relevant if we later let people edit the same document or draft together.

      Failure behavior

      CaseBehavior
      Two sends arrive togetherTransactionally assign unique sequences. Server acceptance determines order, not client clocks.
      A send is retriedUnique (room_id, actor_id, command_id). Return the original acknowledgment.
      Reply streamsBridge batches deltas every 200 ms or 16 KiB, whichever comes first. Persist each accepted batch and the message projection before broadcasting.
      Reply cannot streamKeep the empty reply at its saved position. Apply one final output event with the same message ID.
      Runner disconnectsShow stalled state after its lease expires. Resume from its durable outbox or mark interrupted; never rerun paid work automatically.
      A client reconnectsReplay after event_seq, or fetch a snapshot plus later events. Slow clients reconnect rather than growing unbounded buffers.
      Run is stoppedOwner or authorized member sends explicit stop. Preserve partial text. Mark stopping, then stopped when the bridge confirms; late output is rejected.
      Membership is revokedUpdate room authorization, close that member's sockets, reject later commands. The room rechecks membership on writes.

      1. Authenticate the sender and check room membership and agent ownership.
      2. In one short transaction: deduplicate, allocate sequences, append the event, and update the message projection.
      3. Commit, then acknowledge and publish the committed event.
      4. Clients apply events by sequence; a pending local send becomes committed only after acknowledgment.

      Use a runner lease plus fencing epoch so only one authorized bridge can publish a run's output. Every delta carries its run ID, epoch, and chunk index.

      Scaling

      • Cloudflare distributes separate chats across room objects. One very busy room still has a throughput and storage limit.
      • The paid per-object SQLite storage limit is 10 GB. Archive old log segments and artifacts to object storage, retaining snapshots and replay boundaries. Limits.
      • Keep versioned events and exports portable. Postgres can reproduce the protocol later, though moving clients and live rooms requires a deliberate migration.
      • Measure pilot agents streaming in the same channel before claiming scale or monthly cost. Measure active duration, writes, fan-out, replay volume, and socket counts.

      Recommendation is an architectural judgment for this workload. Prices are vendor-listed baselines, not comparable all-in hosting quotes.

      What to control

      • Batch stream updates at the local bridge, rather than sending one event per token.
      • Let the room handle short incoming events and return. The agent's long run stays on the local machine.
      • Avoid a room timer or outbound model connection that keeps it resident. Use hibernatable sockets and durable alarms when needed.
      • Apply per-room limits for event size, rate, history retention, attachments, and concurrent runs. Meter and alert on costs; an alert is not a hard spending cap.
      • Model spend remains each participant's responsibility. The backend estimate covers collaboration infrastructure only.

      OpenAPPA

      A possible local policy layer between an agent and its tools.

      OpenAPPA checks permitted information flows before tool calls. Its engine can run embedded or as a sidecar. Repository and MIT license.

      Where it helps this project

      QuestionProposed use
      Can this agent read shared content?Carry participant provenance, audience, and trust into an adapter's policy input.
      Can a tool send that content elsewhere?Evaluate the tool's destination and effects before execution.
      Who approves local actions?The runner's owner sets policy; :o room membership remains a separate authorization check.

      Integration requirements

      • A harness hook must be able to stop a tool call and withhold or replace its result. A terminal stream alone cannot enforce the policy. Integration contract.
      • Map shared-message sources and tool behavior to explicit labels and contracts. Audience and trust have distinct roles. Policy model.
      • Do not claim universal harness coverage. Check hook capabilities adapter by adapter.
      • The repository describes preview/RFC status and potentially breaking interfaces. Pin a revision for an integration experiment.

      MVP decision

      • Include policy and approval capabilities in the adapter design.
      • Keep an OpenAPPA experiment separate from chat synchronization.
      • Require owner approval for remote agent requests until the intended policy is agreed.

      Meaningful contribution

      • Let owners define what counts as useful: unanswered calculation, requested artifact, assigned task, or another explicit condition.
      • Start with inexpensive event rules. Model-based detection also consumes tokens and sends context to a model; give it its own budget.
      • Conditions ignore agent-authored messages by default. Record the triggering event ID and causal chain; deduplicate and limit chain depth to stop loops.
      • Show why a run started, who owns it, and which context it read. Provide pause, stop, and room-level quiet controls.
      • Do the work and return the result. Do not add commentary to every human message.

      Chat behavior

      DraftsTyping remains local until Send. Pending sends are separate from saved history.
      RepliesSave a reply position before generation, then fill it in place.
      InterruptionsNew human messages do not interrupt text or rewrite another reply. Stop a run explicitly; changing its prompt requires a new run or a supported harness action.
      NotificationsUnread state, human mentions, agent completion/failure, mute per channel. Agent activity must not drown out messages from people.
      ControlsShared composer selects recipients. Native terminal pane handles uncovered harness settings and hotkeys.

      Groups and hordes

      EntityPurpose
      WorkspacePeople, projects, agent directory, and shared rules.
      Channel / direct chatDurable ordered conversation, with its own audience and agent settings. Direct chats can have two or more people.
      HordeA coordinated group of agent runs, backed by contributors' models, token budgets, and compute.
      MissionGoal, task graph, contribution offers, results, and acceptance criteria.

      Large missions

      Split workUse task rooms and bounded work items. A mission summary contains selected findings, not every token from every agent.
      Claim tasksAtomic task claim with a lease, owner, attempt, and fencing epoch. Prevent duplicate ownership; keep retries explicit because tools and paid runs cannot be made exactly-once.
      ContributeEach contributor keeps API keys or local models, chooses allowed tasks, and caps spending. Owners can withdraw availability.
      Parallel runsIndependent sessions can run together. Serialize work on one native session. Use branches/worktrees and artifact versions to avoid shared-file conflicts.
      Exchange findingsHand off exact context, artifacts, uncertainty, and evidence. Share useful discoveries between groups deliberately.
      ValidateSeparate result submission from acceptance. Math claims need checking or formal verification where applicable; patches need review and relevant evidence.
      Bound scaleRoom rate limits, bounded subscriptions, stream batching, snapshots, archived history, task quotas, and budget controls.

      For example, a community could investigate an open math problem with independent approaches and a review group. More agents do not establish correctness.

      Group collaboration is the core model. Massive community missions are a later implementation phase.
